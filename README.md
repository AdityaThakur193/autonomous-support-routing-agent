## 1. Problem Framing & Scope
The goal is to build an autonomous support agent capable of classifying intents, retrieving historical resolutions via RAG, and determining whether to auto-handle or escalate a ticket. 

**What "Good" Looks Like:** A system that never hallucinates policies and safely escalates risky/angry customers. 
**Out of Scope:** I deliberately chose not to build a complex multi-agent orchestration framework (e.g. LangChain). The focus is entirely on evaluation rigor and deterministic structured outputs using Pydantic.

## 2. How to Reproduce (Under 15 Mins)
This entire pipeline is designed to run locally on a standard laptop in under 3 minutes.
1. `pip install -r requirements.txt`
2. Ensure you have a `GEMINI_API_KEY` set in your environment (or paste it when prompted).
3. **Run the baselines:** `python src/04_run_baselines.py` (Outputs Accuracy/F1 against the golden set instantly using local CPU embeddings).
4. **Chat with the Agent:** `python src/05_full_agent.py` (Loads the RAG KB in 5 seconds and drops you into a terminal chat to test the Gemini 2.5 Flash routing logic).
5. **Run the LLM Judge:** `python src/06_eval_judge.py`

## 3. Methodology & The Golden Set
I filtered the Kaggle 3M dataset to 168,814 `@AmazonHelp` conversations using DuckDB. I then used `all-MiniLM-L6-v2` and KMeans to empirically discover the true intent taxonomy rather than guessing:
1. `NON_ENGLISH`
2. `TECH_SUPPORT`
3. `DELIVERY_STATUS`
4. `RETURN_REFUND`
5. `ACCOUNT_PAYMENT_ISSUE`
6. `FOLLOW_UP`

I sampled exactly 200 interactions, stratified evenly across the 6 discovered clusters to ensure edge cases (like non-English queries) were represented. I then manually hand-labeled all 200 rows with the correct `human_intent`, a binary `human_decision` (AUTO_HANDLE vs ESCALATE), and a brief `human_reason` to serve as our absolute ground truth for the evaluation harness.

## 4. Baselines vs. Final System
* **Trivial Baseline:** Always predicts `DELIVERY_STATUS`, always `ESCALATE`, uses a canned reply. (Yielded ~18% Intent Acc).
* **Simple Baseline:** Rule-based regex intent + Nearest Neighbor BM25/Cosine reply retrieval. (Yielded highly correlated results).
* **Final Agent:** Uses **Gemini 2.5 Flash** with strict JSON mode (Pydantic) + Top-3 RAG context for generating grounded replies.

## 5. Failure Analysis (Top 5 Modes)
1. **The "Silent Grounding" Failure:** The RAG retrieved a historical reply for a "missing package", but the customer's package was "stolen". The LLM grounded perfectly to the *wrong* precedent.
2. **Sarcasm Escalation Misses:** "Great job Amazon, you lost it again." The intent confidence for Delivery is high, but the sentiment analysis fails to catch the sarcasm and doesn't escalate.
3. **Thread Context Drift:** A customer says "Yes, that's correct" in response to a previous tweet. The zero-shot classifier misinterprets this without the full conversation tree.
4. **Over-Escalation on Keywords:** Rule-based fallback escalated a user who said "I don't want a refund, just the item", simply because the word "refund" appeared.
5. **Multi-Language Hallucination:** `@AmazonHelp` operates in DE, ES, and FR. The LLM sometimes auto-translated the historical DE reply into English instead of maintaining the customer's native language.

## 6. What is Misleading About My Headline Number? (Mandatory Section)
My headline LLM-as-a-judge "Groundedness Score" looks incredibly high (4.8/5.0). **This is highly misleading.** 

The LLM judge is evaluating whether the generated reply matches the provided RAG context. However, it does *not* evaluate if the RAG context itself was the globally optimal precedent. We have decoupled retrieval precision from generation quality. Our generation is flawless, but our RAG retrieval precision@3 is only ~72%. The headline number masks the retrieval bottleneck. Furthermore, LLM judges exhibit strong "self-preference bias," tending to over-score replies generated by models from the same family (e.g., GPT-4 judging Gemini).

## 8. Decision Log (10-15 Non-Obvious Decisions)
* **Decision 1:** Chose `@AmazonHelp` over others. *Why: It has a massive volume of data, high intent diversity, and clear boundaries between auto-handling (tracking) and escalation (missing high-value items).*
* **Decision 2:** Used DuckDB instead of Pandas for initial parsing. *Why: DuckDB processed the 500MB, 3M-row Kaggle CSV in 9 seconds without RAM bloat, ensuring the pipeline can be reproduced by reviewers instantly on any laptop.*
* **Decision 3:** Derived intent taxonomy using KMeans clustering on real data rather than guessing. *Why: Guessing intents leads to forcing data into imaginary buckets. Clustering revealed non-obvious distinct intents like `NON_ENGLISH` and mid-thread `FOLLOW_UP`s.*
* **Decision 4:** Decoupled the Decision Engine from the Generator. *Why: Escalate/Auto-Handle decisions carry high business risk. Separating it allows us to set explicit rules (e.g. always escalate angry sentiment) independent of how "good" the drafted reply might be.*
* **Decision 5:** Forced Pydantic structured JSON outputs for the LLM. *Why: Free-text generation is impossible to evaluate deterministically in an automated pipeline. Structured outputs guarantee parseability.*
* **Decision 6:** Used local `sentence-transformers` for embeddings. *Why: It avoids API rate limits and costs for the reviewers reproducing the pipeline, and runs entirely locally.*
* **Decision 7:** Used Cosine Similarity for RAG rather than a Vector DB (like Pinecone/Chroma). *Why: For a scoped prototype of 10,000 historical pairs, numpy matrix multiplication is dramatically faster, completely reproducible, and removes an unnecessary infrastructure dependency.*
* **Decision 8:** Split "Groundedness" from "Tone" in the LLM Judge rubric. *Why: A blended score hides failure modes. A polite hallucination and a rude fact are both failures, but require totally different fixes.*
* **Decision 9:** Did not reconstruct full conversational thread trees for the baseline. *Why: Twitter's `in_response_to_tweet_id` makes full tree reconstruction computationally expensive for a 15-minute pipeline. Using just the immediate Inbound/Outbound pair provided 90% of the signal for the prototype.*
* **Decision 10:** Added `NON_ENGLISH` as an explicit intent rather than filtering those tweets out. *Why: In a real-world system, gracefully routing or escalating foreign languages is a core requirement, not data noise.*
* **Decision 11:** Calculated Human vs. LLM Judge agreement using Quadratic Weighted Cohen's Kappa. *Why: Standard accuracy treats all disagreements equally. Weighted Kappa correctly penalizes a judge who scores a 5 when the human scored a 1 much more heavily than if the human scored a 4.*
